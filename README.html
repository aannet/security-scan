Security Kit

Un poste de travail de sécurité pour un dépôt de code : un scan déterministe en conteneur, plus un audit mené par un agent, avec des rapports vérifiables.

But Vue d'ensemble Scanner Audit par agent Utilisation Arborescence Limites

À quoi sert ce kit

Ce kit sert à examiner la sécurité d'un dépôt cible (aujourd'hui 002-wnext) sans rien installer sur le poste et sans jamais modifier le dépôt. Il combine deux approches complémentaires :

  • Le scan : des outils classiques, reproductibles, qui cherchent des problèmes connus (secrets, dépendances vulnérables, motifs de code dangereux).
  • L'audit : un agent à outils qui lit le code, formule des hypothèses d'attaque, les fait contredire par d'autres agents, et produit des constats sourcés.

Le scan répond à « y a-t-il un problème déjà répertorié ? ». L'audit répond à « existe-t-il une faille propre à ce code ? ». Aucun des deux ne remplace l'autre.

Vue d'ensemble

1. Scan déterministe

Image Docker avec gitleaks, OSV-Scanner et Semgrep aux versions épinglées. Même entrée, même sortie.

2. Audit agent

Skill Cloudflare security-audit : reconnaissance, chasse, validation adverse, rapport.

3. Contrôle validation

Les validateurs du skill vérifient que findings.json et coverage-ledger.json respectent le schéma.

Le scanner (scanner/)

Une image locale reproduit npm run scan du dépôt cible. Le code scanné n'est jamais copié dans l'image : il est monté en lecture seule sur /src, et les rapports sortent dans un dossier séparé monté sur /out.

Garanties d'isolation

  • Utilisateur non root, système de fichiers en lecture seule (--read-only), seul /tmp est inscriptible.
  • Aucune capacité Linux (--cap-drop ALL), pas d'élévation (no-new-privileges), mémoire plafonnée (--memory 4g), 512 processus au plus.
  • Binaires téléchargés vérifiés par somme SHA-256 ; skill cloné à une révision git précise dont le hash est contrôlé.

Codes de sortie

Le scan échoue (code 1) sur un constat critique ou une erreur d'outil. Avec --strict, il échoue aussi sur un constat haut. Le résumé est écrit dans resume.json, à côté des rapports bruts de chaque outil.

L'audit par agent (.agents/skills/, audits/)

Le skill cloudflare/security-audit-skill (licence MIT) transforme un agent de code en auditeur. Il est installé dans .agents/skills/security-audit et sa version est figée dans skills-lock.json (hash de contrôle). Sa licence est dans LICENSES/. L'image Docker clone sa propre copie, épinglée à une révision.

Les six phases

  1. Reconnaissance : architecture, frontières de confiance, surfaces d'entrée, registre de couverture (coverage-ledger.json).
  2. Chasse guidée par la couverture : des chasseurs isolés prennent chacun des unités du registre ; des critiques cherchent les trous.
  3. Validation des candidats : chaque piste est confiée à un vérificateur neuf dont le travail est de la réfuter.
  4. Sortie structurée : findings.json, validé contre report-schema.json.
  5. Vérification indépendante : de nouveaux agents revérifient les affirmations sur le source.
  6. Rapports : REPORT.md, FINDINGS-DETAIL.md, NEEDS-VALIDATION.md.

Les trois verdicts

VerdictSens
confirmedTrace complète dans le source, résultat observable borné, sévérité attribuée.
needs_validationPiste sérieuse bloquée sur un fait précis non vérifiable (souvent une exécution ou une config de déploiement). Aucune sévérité.
rejectedCandidat réfuté, conservé avec la raison pour ne pas être réexaminé.

Principes

  • L'agent qui vérifie n'est jamais celui qui a trouvé.
  • La sévérité vient de la probabilité × l'impact, pas d'un écart à une liste.
  • Une défense en profondeur manquante est une note de durcissement, pas une vulnérabilité.
  • Les runs s'additionnent : chaque passage cible les trous du précédent.

Utilisation

Lancer un scan

./scan.sh /chemin/vers/un/depot              # n'importe quel dépôt, git ou non
./scan.sh /chemin/vers/un/depot --strict     # échoue aussi sur un constat haut
./scan.sh /chemin/vers/un/depot --audit=audits/002-wnext/run-1

Seule dépendance : Docker. L'image security-kit:1 se construit au premier lancement. La progression s'affiche en console ; le rapport final est un dashboard report.html dans reports/<horodatage>-<dépôt>/. Budget : 10 minutes maximum, étapes en parallèle (30 à 50 s mesurées sur 002-wnext). Détail : scanner/README.md.

Lancer un audit

Dans une session d'agent de code ouverte sur le dépôt cible, avec le skill disponible :

security audit this codebase

Les livrables arrivent dans audits/<dépôt>/run-N/. Relancer crée un nouveau run-N qui s'appuie sur les précédents.

Limites à connaître

Pas d'exécution du code cible. L'audit actuel est une analyse du source seulement : pas de sandbox imposée par l'OS, donc aucun test dynamique. Ce qui exigerait une exécution reste classé needs_validation.
  • Réseau : nécessaire pour OSV-Scanner. Les règles Semgrep sont figées dans l'image au build.
  • Configuration : les exclusions et seuils viennent de tests/security/ du dépôt scanné, pas de l'image. Les modifier ne demande pas de reconstruire.
  • Architectures : image native amd64 et arm64 (Mac Apple Silicon, Graviton), choisie selon l'hôte.
  • Versions : changer un outil impose de changer la version et les deux sommes SHA-256 (amd64, arm64), dans le Dockerfile seulement.
  • Le skill n'est pas lancé par le conteneur : c'est un workflow d'agent multi-phases qui demande un modèle. Le conteneur ne fait que le valider.
  • Une passe ne suffit pas : selon les auteurs du skill, un seul run trouve environ la moitié de ce que des runs répétés trouvent au total.
