Security Kit · note de cadrage

Un audit de sécurité reproductible, sans rien installer sur le poste

Ce que le kit fait, pourquoi il est construit comme ça, où il en est, et la décision à prendre pour la suite.

En bref
  • Deux couches : un scan déterministe en conteneur, un audit par agent avec preuve et vérification indépendante.
  • Le dépôt cible est monté en lecture seule. Le kit n'écrit jamais dedans.
  • Premier run sur un dépôt applicatif : 3 constats confirmés, 9 à valider, 2 rejetés. Aucun critique ni élevé.
  • Reste à trancher : sandbox d'exécution d'abord, ou run-2 d'audit (voir fin).

Le problème

Un scanner seul sort du bruit sans jugement. Un agent seul sort du jugement sans preuve. Dans les deux cas, quelqu'un doit trier à la main, ce qui veut dire que le coût réel d'un audit, c'est le temps d'un senior, pas la puissance de calcul.

Le kit vise l'inverse : un résultat qu'on peut lire en dix minutes et dont on connaît le niveau de preuve, sans toucher à la machine ni au dépôt.

Ce que fait le kit

1. Scangitleaks, OSV-Scanner, Semgrep dans une image Docker aux versions épinglées. Même entrée, même sortie.
2. AuditUn agent suit le skill security-audit en six phases : recon, chasse, validation adverse, sortie structurée, vérification, rapport.
3. ContrôleLes validateurs du skill vérifient que findings.json et coverage-ledger.json respectent le schéma.

Le scan dit « y a-t-il du connu ? ». L'audit dit « y a-t-il une faille propre à ce code ? ». On ne remplace pas l'un par l'autre, donc on garde les deux.

Choix de conception

  • Lecture seule partout. Dépôt monté en :ro, conteneur --read-only, --cap-drop ALL, utilisateur non root, mémoire plafonnée à 3 Go (la WSL a déjà planté deux fois sur la mémoire). Seuls /tmp et /out sont inscriptibles.
  • Tout est épinglé. Binaires vérifiés par SHA-256, skill cloné à un commit précis dont le hash est contrôlé, puis historique git supprimé.
  • Config côté cible, pas côté image. Exclusions et seuils viennent de tests/security/ du dépôt scanné, donc changer une exclusion ne demande pas de rebuild.
  • Parité avec le dépôt. Même logique de sévérité et mêmes versions que le script de scan du dépôt d'origine, ce qui veut dire que les deux doivent rester alignés (URL et somme, dans les deux fichiers).
  • Sorties séparées. Rapports du scan dans reports/<horodatage>-<dépôt>/, audits dans audits/<repo>/run-N/. Rien ne se mélange avec le code audité.
  • Un verdict = un niveau de preuve. confirmed a une trace source et une sévérité. needs_validation nomme le fait manquant et n'a pas de sévérité. rejected garde sa raison.

Ce qu'on emprunte à Cloudflare

L'audit repose sur le skill open source cloudflare/security-audit-skill (MIT), à la révision c1c8a8c épinglée dans le Dockerfile. On ne l'a pas réécrit : on a pris sa discipline, c'est-à-dire exiger une frontière franchie et un résultat concret avant tout constat, faire réfuter chaque candidat par un agent distinct de celui qui l'a trouvé, ne jamais attribuer de sévérité à ce qui n'est pas prouvé, tenir un registre de couverture qui montre aussi ce qui n'a pas été regardé, et n'exécuter la cible que sous bac à sable OS. Notre apport se limite à l'enveloppe : isolation, épinglage, validation automatique de la sortie, et branchement sur le scan.

Résultat du premier run

Cible : un dépôt applicatif (environ 800 fichiers), profil standard, analyse source uniquement.

3confirmés
(bas, moyen)
9à valider
2rejetés
19unités de couverture
  • Le plus important est classé « à valider » : il dépend de la configuration de déploiement, que le code ne peut pas garantir. La question part donc au propriétaire du déploiement.
  • Sur les 19 unités : 7 couvertes, 9 candidates, 2 différées, 1 hors périmètre. Les trois dernières catégories sont déclarées dans le rapport, pas passées sous silence.
  • Le scan de son côté n'a trouvé aucun secret, aucun critique ni élevé ; 2 moyens et 2 bas sur une dépendance, 3 moyens Semgrep dans un script tiers.

Ce qui manque

  • Pas de bac à sable OS. Aucun code cible n'a été exécuté. Tout ce qui demande une exécution reste en needs_validation. C'est le plus gros plafond sur la valeur de l'audit aujourd'hui.
  • Un run ne suffit pas. Les auteurs du skill indiquent qu'une passe trouve environ la moitié du total sur des runs répétés. Un seul run-1, donc.
  • Pas de suivi dans le temps. Le scan est générique (./scan.sh <dépôt>, moins d'une minute mesurée) mais chaque run est isolé : pas de CI, pas de tendance.

Priorités (80/20)

  • Traiter les 9 needs_validation avec les owners : c'est là qu'est la valeur immédiate, pour un coût faible.
  • Lever le plafond d'exécution : un sandbox OS conforme, sinon l'audit reste statique.
  • Faire un run-2 sur le même dépôt : les passes sont additives, donc c'est le meilleur ratio coût / couverture gagnée.
  • Reporter à plus tard : CI et suivi dans le temps.
Décision attendue. On investit d'abord dans le sandbox OS pour que l'audit puisse exécuter et trancher les 9 pistes, ou on lance un run-2 immédiat en analyse source et on traite les needs_validation à la main avec les owners ?
